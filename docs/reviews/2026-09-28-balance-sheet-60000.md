# 60,000-instrument balance sheet benchmark

Measured locally on September 28, 2026. This report measures actual product
engines and the complete prototype decision workflow, rather than synthetic
precomputed position contributions.

## Workload and measurement boundaries

| Setting | Value |
|---|---|
| Core instruments | 60,000 distinct contracts |
| Additional balance sheet positions | 6 money-market positions, 3 swaps, 2 swaptions |
| Market scenarios | Base, parallel +25 bp, parallel -25 bp |
| Monte Carlo paths | 128 for both calibration and sensitivities |
| Earnings and strategy horizon | 27 months |
| Cashflow simulation grid | Up to 360 months |
| Strategy coefficients | 35 candidate cohorts per market, 105 across three markets |
| Pricing threads | 4 Numba threads |
| Hardware | Intel Core i7-14700, 20 physical / 28 logical cores, 32 GB installed RAM |
| Software | Windows 11, Python 3.12.11; Rust session with native C++ HiGHS; existing Python/Numba product engines |
| Calculation cache | 512 MiB retained-result limit, 500,000-entry limit |

The synthetic fixture expands each of the original 375 positions into 160
contracts. Mortgage WAC, loan/debt coupons or spreads, CD rates, and deposit
account sizes vary across the new contracts. Identifiers and economic terms are
checked for uniqueness. Notionals are divided across the contracts, preserving
the original balance sheet size and product mix: approximately **$18.91 billion
of modeled assets** and **$1.803 billion of EVE**. This is a position-count scale
test, not a claim about a particular institution's actual holdings.

| Book | Instruments |
|---|---:|
| MBS and residential whole loans | 19,200 |
| Commercial and auto loans | 14,400 |
| Long-term debt | 4,000 |
| Non-maturity deposits | 16,000 |
| CDs | 6,400 |
| **Total core instruments** | **60,000** |

The decision workflow includes original product optionality and behavioral
models, base OAS calibration, fixed-OAS scenario valuation, parallel DV01,
monthly NII/runoff, EVE/LCR/NSFR/CET1, strategy-library construction, robust
optimization, and independent allocation replay. The key-rate stage separately
adds ten tenor sensitivities across all five core books at the base market.

**Excluded:** nonlinear forward stress, vega, forecast-conditioned NII, dynamic
reinvestment, execution, API/network/browser latency, concurrent users, and
distributed operation. The EVE +/-200 bp KPI is a first-order DV01 estimate,
not a nonlinear +/-200 bp stress run. The 128-path setting matches the prior
prototype comparison; the engine's default MBS base setting is 512 paths.
No accuracy or capacity claim at that higher setting is inferred here.

Individual pricing rows are components of session initialization; do not add
them to the initialization total. Full builds and key-rate analytics were each
measured once. The fresh rebuild is a separate full run from an empty dependency
cache. Compilation artifacts already existed on disk, so these are not
first-install/JIT compilation measurements. This workstation was not an isolated
benchmark host; timings are observations, not service-level guarantees.

Only one instrument is repriced for a single-instrument edit; the 100-loan edit
reprices exactly 100. Constraint changes reprice no instruments and rebuild no
templates. The initial native request stream is approximately 15.9 MiB; observed
single-instrument updates send only 475–543 bytes. The native boundary therefore
does not ship the 60,000-position book on each interaction.

The optimization dimension remains 35 candidate cohorts, not 60,000 decision
variables. This benchmark validates a large backbook feeding the current
strategy LP; it does not establish capacity for 60,000 independently optimized
trades or mixed-integer optimization.

## Memory and cache behavior

The Windows process-lifetime peak resident working set was **2.07 GiB**; peak
process commit was **3.66 GiB**. The key-rate stage's sampled peak resident set
was 2.06 GiB. At least 5.45 GiB of physical memory remained available during
that stage. These totals include Python, Numba, the native library and temporary
arrays; they are not the same as the 512 MiB retained-result cache budget.
No claim of a 512 MiB process-memory ceiling is made.

The initial session used an average of 3.10 CPU cores over its wall time; the
key-rate stage averaged 3.17. Four pricing threads were enabled on a machine
with 28 logical cores. All-core performance was not measured.

The first base-market pass computed **204,060 instrument cashflow nodes**.
Three distinct legs per instrument would require 180,000 nodes. The additional
24,060 computations occur when earlier nodes are evicted and then requested
again for income calculations: 16,893 mortgage nodes and 7,167 deposit nodes.
The cache ends almost exactly at its 512 MiB limit. This is measured repeated
work, not an assumption that a larger cache must improve total performance.

## Validation

- All 60,000 identifiers and economic contracts are distinct within their books.
- Expanded book notionals reconcile to the seed book to a relative tolerance of 1e-12.
- Every core instrument returns a price. Maximum calibration error across the five books is below 0.000001 price points.
- Initial and edited native solutions pass independent Python allocation and constraint replay.
- Native and SciPy objectives on identical coefficients differ by less than $0.000001.
- The fresh full rebuild differs from the initial native objective by $0.00000143.
- The key-rate run returns ten finite tenor sensitivities plus parallel DV01 for every core book. It preserves base book market values and total NII within the benchmark tolerances.
- All engine source hashes were unchanged between the start and end of measurement.
- The full engine regression suite passed: **95 tests, zero skips**, in 42.82 seconds. Tests ran after the benchmark, avoiding measurement interference.
- A separate 375-position smoke run passed the runner's complete workflow, including key-rate analytics and the smaller loan-batch case.

These are implementation and numerical consistency checks on synthetic inputs.
They do not validate behavioral assumptions against production data. Regulatory
weights and capital projections retain the prototype's documented approximations.

## What this says about the Rust migration

About **98.3% of initialization time is inside product pricing and analytics**.
Moving additional orchestration or the LP wrapper to Rust cannot remove that
work. The native session already makes local edits fast by changing only the
affected positions and maintaining a small optimization model.

The persistent native solve is approximately 1.6 times faster than the fresh
SciPy call on the same coefficients in this run, but both ultimately use native
HiGHS. That comparison combines model reuse and wrapper differences; it is not
a measurement of Rust versus Python numerical kernels. For small allocation
replay, the existing Python/NumPy evaluator is faster than the JSON/native path.
Both are comfortably below one millisecond in-process.

Recommended optimization order based on this run:

1. **Avoid recomputing live base cashflows.** Reuse request-local base results
   for income calculations even when the global LRU has evicted them. Separate
   small calibration/path metadata from large cashflow arrays, and measure a
   cache-budget sweep before choosing a larger default.
2. **Profile the full product pipeline.** Attribute time to mortgage/deposit
   kernels, schedule construction, hashing, freezing/copying, and accounting.
   Retain bounded batches and measure more thread counts before a broad port.
3. **Port measured hot paths behind the existing batch interface.** Require
   fixed-OAS, CRN, accounting, and product parity gates. This benchmark supplies
   the 60,000-contract workload for that comparison; it does not measure a Rust
   rewrite of the pricers.
4. **Scale the other dimensions explicitly.** More paths, markets, candidate
   cohorts, nonlinear stress horizons, and concurrent sessions are separate
   workloads. A large backbook with a small LP does not establish their limits.
