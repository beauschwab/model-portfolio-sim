# Streamed realized credit ledger

`credit-path-ledger-1` is an explicit native route for realized physical credit paths. It adopts [credit path accounting](credit-path-accounting.md) into actual balanced opening/event journals, source daily states, recovery claims and account closing reports. Legacy `credit-ledger-1` protocol 4, dated protocol 3 and legacy monthly overlays retain their existing economics. Choosing this new schema is required; it never silently changes a saved legacy book.

The Rust interfaces are `CompiledPathLedger::compile(request)`, `compile_with_limits(request,max_positions,max_work)`, `normalized_spec()`, `admitted_work()`, `validate_json(input,max_positions,max_work)` and `run(compiled,writer)`. The complete synthetic example is [credit-path-ledger-1.json](../../examples/models/credit-path-ledger-1.json). Root adapters own transport, immutable input/result storage, independent persisted verification and publication. This module does not certify 60,000-position acceptance, empirical calibration or full tracker #25 completion.

## Input ownership and coverage

The strict request contains `schema`, `monetary_unit`, `as_of_ordinal`, a raw normalized daily `specification`, and complete `runs`. Each run specifies `run_id`, `scenario_id`, numeric `severity` and `batches`. Each batch has a unique `batch_id`, explicit `account_by_position` records (`position_id`,`account_id`) and a complete `request` under `credit-path-accounting-1`. There are no callbacks or Python calculations.

The normalized specification supplies accounts, equity/cash openings, loan anchors, scenarios and reverse severities. Every run must contain exactly one realized owner for every position. Baseline at severity 1, every named scenario at severity 1 and every requested reverse severity require supplied run coverage. A run identity is unique; duplicate run/scenario/severity, duplicate position ownership, duplicate claims, unmatched path keys, missing account bindings and pricing sources reject. Source ID/revision and policy identities remain attached to the complete raw contract. A scenario may deliberately share supplied draws with baseline, but its economic contract is independently supplied rather than inferred from a severity multiplier.

Owned positions are loans beginning at the as-of day. Legacy PD, migration, draw, monthly runoff, floating beta, mark, collateral and earnings-policy ownership cannot overlap this route. Netting sets, cashflow overlays and generic account fees/costs/tax/dividends are unsupported here. Actual path rates and credit transitions own economics. Principal, undrawn commitment, signed recognized accrual, signed basis and allowance openings must match raw loan anchors and account currency. Position source coverage is absolute; a realized account never receives a survival haircut.

All path batches start at the same as-of midnight and end at the reporting midnight. For any in-report contractual maturity anchor, an explicit supplied `maturity` boundary must match the anchor date. Mismatched or duplicate maturities reject; no maturity is synthesized. A boundary applies to every realized account in its core batch, so heterogeneous maturity/payment calendars require separate batches. Out-of-report principal anchors preserve live exposure and full recovery/interest tails.

`spec::normalize_signed_credit_path` admits signed recognized loan accrual only for this route. It reuses the standard validator with an explicit flag and retains signed amounts in opening equity reconciliation. Standard `normalize` and `validate` retain their original nonnegative accrued-opening domain. No absolute value, sign conversion or equity plug is introduced.

## Batches, staging and cancellation

Structural compilation validates normalized spec, opening anchors, complete coverage, calendars, exclusive ownership, source identities and aggregate admission before writing any rows. It does not project the whole book twice. Execution evaluates one complete core batch, with all core financial/claim/conservation checks, before emitting rows for that batch. A later batch can fail after earlier rows have been written; those rows are staged artifacts, not a completed publication. Any failure, cancellation, deadline or broken output withholds the final completion record. The external persisted verifier and atomic publication guard must also pass before a manifest can be published.

Native cooperative checkpoints run during structural run validation, between bounded financial batches, before each path, during journal emission and during account closing. Core batches are bounded computations; there is no claim of cancellation at each arithmetic operation. Transport watchdogs remain necessary for blocked writes and process termination. The sink buffers at most 1,024 table rows before flushing. Core batch results are dropped before the next batch; the full portfolio's economic daily states are not retained together.

The maximum native admission tier is 60,000 normalized positions and 90 million counted work units, with smaller limits available to callers. These are admission ceilings, not measured scale acceptance. Each core batch admits at most 256 bindings and 250,000 path-days, so its effective binding limit also satisfies `bindings * horizon_days <= 250000`. Core's two million work, 250,000 intents, 32-point per-origin recovery tails and metadata limits still apply. Account closing retains at most 250,000 account-days per run. Aggregate charged raw metadata is at most 32 MiB; complete tail records count even when cash lies beyond the reporting horizon. Compilation charges source/path/day/term/tail work; execution additionally charges the core's actual work. Checked arithmetic fails on count overflow. Component limits do not establish an aggregate RSS cap.

## Journals and source reconciliation

Opening transactions post actual account cash, explicit equity, loan principal, signed accrued right, signed basis and contra-asset allowance. Their sum must balance. Every path intent becomes one journal transaction, using the shared twelve account codes. Cash uses instrument `@cash`; default principal/accrual/basis use the claim ID; live rights, allowance and earnings retain position identity. Every transaction is balanced and currency-bounded. Empty zero posting intents retain source lineage with a null transaction number and consume no journal number.

`transaction_number` is globally contiguous for emitted nonempty transactions. `transaction_key` is a collision-safe JSON tuple string identifying opening account or run/batch/position/intent index. This avoids collisions from delimiters inside supplied IDs. Journal order is stable opening/run/batch/path/intent order. A later source batch can restart dates, so chronology must be checked within each source/position rather than globally across a run. No sorting that changes within-path posting or reduction order is introduced.

The runner independently accumulates daily GL posting deltas and daily source balances, then replays account-day balances from openings. Actual live/default principal, signed accrued rights, signed basis and allowance must match the summed source state. Final per-instrument GL balances must match daily account replay. Account equity changes only by posted earnings. Signed payable interest rights are classified separately per path; opposite rights on other positions cannot cancel the liability classification. `assets = net_assets + liabilities`, while `equity = net_assets` for this loan-only route. No generic liability funding book is inferred.

Recovery claims and complete exact recovery points remain attached after principal default/chargeoff and beyond reporting. The shared accounting policies own allowance, chargeoff, default reversal, signed interest settlement and basis treatment. Economic loss remains distinct from reviewed allowance. This route does not choose accounting standards, infer ECL from synthetic hazards or establish legal/regulatory compliance. Exact economic timing and daily recognition conventions are those documented in [credit path accounting](credit-path-accounting.md).

## Protocol 5 tables

Output consists of newline-delimited `{table,rows}` batches followed only on success by `{complete:true,protocol:5}`. Journal/trial/report common columns follow protocol 4. Nested typed records preserve source details for transport and immutable persistence.

| Table | Retained content |
|---|---|
| `journal` | Transaction number/key, run/scenario/severity, day/ordinal, account/entity/currency, event, GL account, instrument and signed value |
| `credit_path_sources` | Batch/position/path/claim binding, raw source revision, measure/unit, complete reviewed binding and economic path result |
| `credit_path_lineage` | Transaction key/number, exact economic time, accrual slice, original event IDs, contractual policy name, reviewed source/policy revisions, claim and recognition timing |
| `credit_path_daily` | Position/path/claim scope, daily independent probability/maturity and absolute live/default monetary state, earned interest and cash/P&L deltas |
| `credit_path_recoveries` | Complete exact recovery point/identity, recognition date, signed interest, principal and after-reporting flag |
| `credit_path_claims` | Final shared claim rights, reviews, remaining principal tail and settled signed-interest IDs |
| `daily_balance` | Actual account cash, gross assets/payable liabilities, net assets/equity, allowance and reconciliation error |
| `trial_balance` | Closing actual GL balances per account/instrument |
| `summary` | Final cash/assets/liabilities/net assets/equity and maximum reconciliation error |

Independent native fixtures replay journal sums and hand-calculated final amounts, preserve full delayed tails and signed opening rights, reject missing scenario/maturity/account/measure coverage, verify multiple batches with restarting calendars, preserve legacy signed-opening rejection and withhold completion for cancellation, financial failure or broken output. The synthetic example's account opens with cash 10 and net equity 66, earns 0.05 before half-day default, funds a contingent draw 10, receives 66.05 recovery cash and charges off reviewed residual principal/basis against allowance. Final account cash/assets/equity are 66.05. These tests validate contained native mechanics; independent persisted verification, API/treasury bridge acceptance and observed model calibration remain separate gates.

## Verified closing capital bridge

Completed `credit_path_balance_stress` jobs may be selected as `credit_ledger` capital sources. The adapter requires retained `credit-path-balance-partitions-1` publication evidence with independent physical-path reconstruction, source reconciliation and journal replay. It selects native credit protocol 5 from that evidence; a caller cannot select a protocol by adding a field to the capital policy. Protocol 4 retains its existing replay and financial behavior.

The bridge streams retained journal partitions in their original order, independently checks balanced transactions, globally contiguous transaction numbers, collision-safe opening/path identities and chronology within each path, and reconciles every closing GL key. It permits later batches to restart dates. Severity-reverse runs are verified; capital reports select each explicitly supplied severity-one scenario. Run/account/entity/currency labels must remain consistent. Native capital preparation classifies negative live/default interest rights as payable liabilities per instrument, while signed basis and posted allowance remain contra-assets. Its gross assets, liabilities and book equity must match the independently verified closing source, with the explicit policy monetary multiplier.

Posted provision, chargeoff, recovery and earnings enter capital once through actual GL balances. Modeled economic loss is not an extra deduction. Regulatory eligibility, risk weights, undrawn/leverage additions and requirements remain supplied reviewed policy inputs. Realized paths are not admitted as captured expected-flow FTP sources. These synthetic hand cases establish contained bridge mechanics, not observed calibration, regulatory approval or aggregate scale acceptance.
